## 1c. What "staff" means

The definition always lived in `services.permissions.STAFF_ROLES`:
investment_staff, admin, super_admin and owner. It was read from a `roles`
token claim that real tokens never carry, so every caller counted as staff.

In the database, staff status is role membership: `user_roles` → `roles.name`.
`staff_assignments` and `team_members` record **which entities** a staff user
covers (they feed the staff visibility engine); they do not record whether a
user is staff.

AUTHZ1 rule: staff = Super Admin, or an admitted user holding a role in
`STAFF_ROLE_NAMES` in their own org. The 'owner' role exists in no org.

verify_bulkfetchui2 and the menu harness were updated and re-run in this
sprint.

## 1e. How /users/me built the front end's permissions

Before AUTHZ1, `/users/me` called `ensure_user`, then
`rbac.get_user_roles` / `get_user_permissions`. That gave the role-axis grants
only:
- A super admin's set was just whatever their roles held.
- A role-less user got an empty list, which the front end's `canPerm` turned
  into "allow everything".

Now `/users/me` returns the request's Principal:
- the effective permission set (a Super Admin's is the whole catalog)
- `status`, `is_staff` and `is_super_admin`

`canPerm` fails closed.
